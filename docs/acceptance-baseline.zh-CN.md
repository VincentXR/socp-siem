# 默认生产候选验收基线

本基线在尚无业务容量约束时提供可执行的默认决策。数字是验收目标，**不是已测容量、
产品承诺或上线批准**。部署结果必须关联源码版本、配置、负载模型和测试环境。
[容量规划](operations/capacity-planning.md) 中的代码上限不等于本基线的达标证据。

## 目标与判定

| 维度 | 默认目标 | 判定方式 |
|---|---|---|
| 租户 | 10 个活跃租户；负载包含一个占 50% 的热点租户 | 分租户统计时延、拒绝、队列及结果；其他租户不能被饿死 |
| 事件 | 平均序列化大小约 1 KiB，P95 4 KiB，至少包含 syslog、JSON 和端点事件 | 保存实际大小分布、来源分布、字段基数及唯一事件 ID；限制超大/高基数输入 |
| 检测规则 | 每租户 100 条：80 条无状态、20 条窗口/关联；至少 10,000 个活跃状态键 | 固定规则版本、窗口、路由维度；分别验证多租户同名状态隔离 |
| 持续吞吐 | 1,000 EPS，全链路连续 24 小时 | 接收数、唯一入索引数、检测终态、预期告警、DLQ 和 outbox 逐项对账；错误/DLQ 不计入有效吞吐 |
| 突发 | 3,000 EPS 持续 15 分钟，随后回到 1,000 EPS | 无丢失；回落后 15 分钟内积压恢复至突发前水平；期间不得降低安全/持久化约束 |
| 检测延迟 | 无状态规则从触发事件被接收至告警可读 P95 ≤10 秒、P99 ≤30 秒 | 以实际告警 ID 对应触发事件计算；窗口规则单列等待窗口和处理延迟 |
| 检索 | 10 路并发；最近 24 小时限定租户/时间的常用过滤与聚合，P95 ≤3 秒、P99 ≤10 秒 | 固定查询集，分别记录冷/热缓存；超时、拒绝、失败计入报告，不能只统计成功样本 |
| 在线保留 | 原始事件 30 天 | 填充或恢复具有代表性的历史数据后测试检索和删除；短期写入不能证明 30 天保留 |
| 归档 | 180 天 | 默认选用有支持的 S3 兼容服务；验证导出、完整性、访问控制、恢复与保留执行 |
| 单节点故障 | 已确认接收事件无丢失；应用处理 5 分钟内恢复 | 在独立节点上停机，核对唯一事件/告警集合和积压；不声称跨系统 exactly-once |
| 灾难恢复 | RPO ≤15 分钟、RTO ≤4 小时 | 故障前定义一致性切点，恢复数据库、Kafka、索引、对象及必要工作流状态后完成业务对账 |
| 安全 | 跨租户读取/写入、普通用户调用服务接口、未授权采集全部拒绝 | 真实 prod 角色与凭据，校验 RLS、网关证明、防重放、TLS、密钥轮换和审计 |

检测规则集必须包含明确的正常事件、恶意事件、重复事件、乱序及迟到事件，其告警期望由
独立 oracle 给定。吞吐结果需同时提供 Kafka lag、outbox 最老年龄、CPU、GC、堆、数据库
锁等待和索引磁盘水位，不能只报告 HTTP 接收速度。

## 默认部署决策

采用仓库 Helm product overlay 的 API/worker 分离方案。核心有状态中间件使用持久盘，
跨至少三个独立故障域部署或选用满足同等故障隔离要求的托管服务。候选部署取 Kafka
replication factor 3 / min ISR 2；OpenSearch 至少三个数据节点、每索引至少一个副本，
实际副本分配必须满足故障域隔离。生产数据库使用 PostgreSQL 及独立运行/迁移角色；
Redis 使用 noeviction。服务规模最终由测量确定，不把副本个数当作容量证明。

其余 PostgreSQL、ClickHouse、Redis、Temporal、对象存储的 HA/备份能力应由各自运维
方案说明，并实际验证。单机运行三个容器不构成独立故障域。

## 存储预算起点

按平均 1 KiB、持续 1,000 EPS 粗算：每天约 88.5 GB 原始数据，30 天约 2.65 TB；
若索引大小按原始数据的 1.5 倍、一个副本、磁盘使用上限按 70% 预算，在线磁盘约需
11.4 TB。180 天原始归档约 15.9 TB，未计算压缩收益。这只是初始预算：索引倍率、
压缩比和字段基数必须实测。数据库、Kafka 留存、快照、工作流和临时重建空间另算。
70% 是容量规划目标，不是修改 OpenSearch 水位的指令。

## 本地分级验证

资源不足的开发环境用于缩小规模的正确性和恢复实验，不能据此签署上述生产 SLO：

1. 修复回归与模块测试，执行架构、迁移、RLS 覆盖、部署等静态合同。
2. 隔离真实 Kafka/OpenSearch/PostgreSQL 的容器集成与失败语义测试。测试对象必须来自
   当前任务创建的 disposable fixture，不能指向共享服务。
3. 本地全链路具备后，从 10、50、100 EPS 每档 10 分钟逐步加压，查询并发 1→5→10；
   任一阶段出现 OOM、磁盘容量不足、持续不收敛积压或错误率上升，就记录不通过并停止升档。
   不用删业务数据、降低磁盘保护阈值、跳过持久化或放宽鉴权使其通过。
4. 在具备容量的独立环境上执行完整 24 小时、真实留存、多节点故障和灾备验证。

本地压测前需确认全链路负载工具能核对唯一事件和精确告警结果。仓库的 pipeline/chaos
脚本可验证部分正确性，不能直接当作 24 小时容量工具。缺少负载工具或目标环境时应明确
记录该项未执行，不能由单元测试时长推算 EPS。
